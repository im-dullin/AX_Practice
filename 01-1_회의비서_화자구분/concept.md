# 회의비서 (화자 구분 버전) — 프로젝트 개념

> **한 줄 정의**: 회의 음성을 듣고 **누가 무엇을 말했는지**까지 자동으로 라벨링해, *화자별 색상 보고서*를 한 장으로 띄워주는 *AI 비서*.

> 기본 회의비서(`../01_회의비서/`)에 **pyannote.audio** 화자 분리(speaker diarization)를 추가한 *심화 버전*.

---

## 1. 왜 화자 구분이 필요한가

기본 회의비서로 5분 회의를 처리하면:
```
"자 시작하겠습니다 이번 주 신규 리드는 32건이고 박과장이 ROI 분석을 5월 27일까지 공유한다고 했고..."
```
→ 한 줄로 평탄. *누가 무엇을 약속했는지* 흐려짐.

화자 구분 버전:
```
SPEAKER_00: 자, 시작하겠습니다.
SPEAKER_01: 이번 주 신규 리드는 32건이고...
SPEAKER_00: 박과장님, ROI 분석 부탁드립니다. 5월 27일까지요.
SPEAKER_02: 네 알겠습니다. 27일까지 공유드리겠습니다.
```
→ *누가 약속했는지* 명확. Claude가 액션의 owner를 정확히 찍어낼 수 있음.

## 2. 동작 흐름

```
🎵 마이크 / 오디오 파일
        ↓
  ┌─────────────────────────────────┐
  │ ① faster-whisper (전사)          │
  │ ② pyannote.audio (화자 분리)      │  ← 두 모델 동시 실행
  └──────────────┬──────────────────┘
                 ↓ (시간축 매칭 — 누구의 어느 발화)
  SPEAKER_00 / SPEAKER_01 라벨 부착된 텍스트
        ↓
🧠 Claude — 요약·결정·액션·리스크 JSON
        ↓
🎨 HTML 리포트 (화자별 색상 6종)
```

---

## 3. 화자 분리 — 어떤 기준으로?

**핵심**: pyannote는 *내용*과 무관하게 **목소리의 특성**으로만 분리합니다.

### 4단계 알고리즘

```
🎵 입력 오디오
    ↓
① VAD (Voice Activity Detection)
   "여기는 발화, 여기는 무음"
    ↓
② Segmentation
   발화 구간을 1~2초 조각으로 자름
    ↓
③ Embedding (목소리 → 192차원 벡터)
   조각마다 *목소리 특성* 숫자로 변환
   (음역대·음색·발음 습관·호흡 패턴 등)
    ↓
④ Clustering (벡터 군집화)
   비슷한 벡터끼리 묶어 *같은 사람* 판정
    ↓
SPEAKER_00, SPEAKER_01, ...
```

### 비유 — *지문 분류*와 같음

- 두 발화가 *같은 사람*인지 *다른 사람*인지 판단 ✓
- 하지만 *누구의 발화*인지는 모름 — 결과는 익명 라벨 ✗
- *김부장* / *이대리* 같은 실명 매핑은 사람이 직접 (Week 2 미션 후보)

---

## 4. ★ 어디까지 정확한가 — 화자 수 한계

pyannote/speaker-diarization-3.1 은 **공식 화자 수 제한이 없습니다**. 다만 실측 정확도는:

| 화자 수 | 정확도 | 비고 |
|---|---|---|
| **1명** (모놀로그) | ★★★★★ | SPEAKER_00 한 명만 나옴 — 정상 |
| **2~6명** | ★★★★★ | **가장 잘 동작하는 구간** — 일반 회의실 환경 |
| **7~10명** | ★★★ | 정확도 점차 ↓ — 너무 비슷한 목소리끼리 합쳐질 수 있음 |
| **11명 이상** | ★★ | 대형 회의장 — 별도 모델 추천 (예: pyannoteAI Premium) |

**권장 환경**: *2~6명* + *각자 10초 이상 발화* + *마이크 1개로 모두 들리는 거리*.

---

## 5. 정확도에 영향 주는 다른 요소

| 조건 | 정확도 |
|---|---|
| 마이크 품질 (헤드셋 ≫ 노트북 내장) | ★★★★★ |
| 화자별 발화 시간 (각자 10초 이상) | ★★★★★ |
| 너무 비슷한 목소리 (가족·형제 등) | ★★ |
| 동시 발화 (overlap) | ★★★ — pyannote 3.1 은 일부 처리 |
| 짧은 발화 (1~2초만) | ★★ — 임베딩 데이터 부족 |
| 배경 음악·잡음 | ★★ — 사전 노이즈 제거 권장 |

**핵심 인사이트**:
- *발화 시간이 짧으면* 임베딩이 부실 → 화자 합쳐짐
- *비슷한 목소리*는 *같은 화자*로 합쳐짐
- *마이크가 멀면* 임베딩에 노이즈 섞임

→ 회의비서를 *실무에 쓸 때* 헤드셋 또는 회의실 중앙 마이크 권장.

## 6. 결과가 이상할 때 — 디버깅 가이드

| 증상 | 원인 |
|---|---|
| 화자 1명만 나옴 (실제 3명인데) | 마이크가 너무 멀거나 다른 화자 발화가 너무 짧음 |
| 화자가 너무 많이 나옴 (실제 2명인데 5명) | 마이크 노이즈, 또는 같은 사람이 톤·속도를 바꿈 |
| `UNKNOWN` 라벨 | Whisper 세그먼트와 pyannote 시간축이 어긋남 |
| 화자가 *번갈아* 안 잡힘 | 동시 발화(overlap) 구간이 많음 |

**팁**: 결과가 *기대보다 나쁘면* 같은 음성을 *몇 초 더 길게* 녹음해 재시도 — 각 화자에게 *최소 10초+* 의 발화가 확보되면 정확도 급상승.

## 8. 핵심 개념 5가지 — 만들면서 배우는 것

### ① 화자 분리 (Speaker Diarization)
*내용과 무관*하게 *목소리 특성*으로 분리. 4단계 알고리즘. 지문 분류와 동일 원리.

### ② 다중 AI 모델 병합
Whisper(전사) + pyannote(화자) 두 *서로 다른 AI* 결과를 **시간축 매칭**으로 합쳐 *완성된* 결과 만들기 — *AI 시대의 표준 패턴*.

### ③ 환경 변수 + .env 파일
API 키·토큰을 *코드에 직접 넣지 않기*. `.env` 파일에 분리해 git에서도 제외 — *보안 기본기*.

### ④ Gated 모델 라이선스
HuggingFace의 *gated* 모델은 *동의 후 사용*. 모델마다 따로 동의 (`speaker-diarization-3.1` / `segmentation-3.0` / `speaker-diarization-community-1` 3개) — *오픈소스 라이선스 실무*.

### ⑤ 점진적 의존성 추가
기본 회의비서(외부 의존 0)에서 **하나씩** 의존성을 더하는 패턴. 처음부터 모든 걸 박지 말고, *진짜 필요할 때* 추가 — *실무 설계 원칙*.
